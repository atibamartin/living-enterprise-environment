# Windows IOC Analysis — SMB Authentication Activity from Kali Linux

## Living Enterprise Environment — Phase 1 / v3 Windows Integration

---

## 1. Overview

This lab examined Windows authentication telemetry generated by a Kali Linux system interacting with the Living Enterprise Environment Active Directory domain controller.

The original objective was straightforward:

1. Generate a failed authentication attempt from Kali Linux.
2. Identify the resulting Windows Security events.
3. Extract useful indicators of compromise or investigation indicators.
4. Correlate attacker-side activity with defender-side telemetry.
5. Generate a small controlled credential-testing sequence.
6. Determine how repeated failed authentication attempts and a successful authentication appear in Windows logs.
7. Identify opportunities for future SIEM detections.

The exercise did not follow the expected path exactly.

The first SMB authentication attempt that was intended to fail instead successfully authenticated. Rather than restarting the exercise or ignoring the unexpected behavior, the investigation pivoted based on the observed evidence.

That resulted in a more realistic analyst workflow:

```text
Expected Activity
      ↓
Observed Result
      ↓
Validate Evidence
      ↓
Investigate Unexpected Behavior
      ↓
Generate Controlled Activity
      ↓
Correlate Multiple Data Sources
      ↓
Identify Indicators
      ↓
Develop Detection Hypotheses
```

This reinforced one of the primary methodologies of the Living Enterprise Environment:

```text
Build → Baseline → Generate Activity → Investigate →
Identify Indicators → Detect → Engineer Detections
```

---

# 2. Lab Objective

The primary objective of this exercise was to understand how Windows records remote SMB authentication attempts originating from an external Linux system.

Specific goals included:

- Generate Windows network authentication activity from Kali Linux.
- Observe successful and failed SMB authentication.
- Analyze Windows Security Event IDs associated with the activity.
- Correlate authentication attempts by:
  - username
  - source workstation
  - source IP address
  - timestamp
  - authentication protocol
  - logon type
  - status and substatus codes
- Compare attacker-side results with defender-side telemetry.
- Examine Active Directory account-state attributes.
- Generate a small controlled credential-testing sequence using Hydra.
- Identify behavioral patterns that could later become SIEM detection logic.
- Document unexpected behavior rather than removing it from the lab narrative.

# 5. DNS Investigation

The following command was initially used:

```bash
nslookup LEE-WIN-SRV-01.livingenterprise.lab
```

The query failed:

```text
Server: 192.168.133.2

** server can't find LEE-WIN-SRV-01.livingenterprise.lab: NXDOMAIN
```

At first this appeared to indicate a possible Active Directory DNS problem.

However, the resolver configuration on Kali revealed:

```bash
cat /etc/resolv.conf
```

Result:

```text
# Generated by NetworkManager
search localdomain
nameserver 192.168.133.2
```

Kali was using the VMware NAT DNS resolver rather than the Active Directory DNS server.

The Active Directory DNS server was then queried explicitly:

```bash
nslookup LEE-WIN-SRV-01.livingenterprise.lab 192.168.133.130
```

Result:

```text
Name:    LEE-WIN-SRV-01.livingenterprise.lab
Address: 192.168.133.130
```

An Active Directory service record was also tested:

```bash
nslookup -type=SRV _ldap._tcp.dc._msdcs.livingenterprise.lab 192.168.133.130
```

Result:

```text
_ldap._tcp.dc._msdcs.livingenterprise.lab
service = 0 100 389 lee-win-srv-01.livingenterprise.lab.
```

## Finding

Active Directory DNS was functioning correctly.

The failure occurred because Kali's normal resolver was:

```text
192.168.133.2
```

while Active Directory DNS was:

```text
192.168.133.130
```

This reinforced an important troubleshooting distinction:

```text
Network Connectivity
        ≠
Service Availability
        ≠
Name Resolution
```

Because Kali represents an attacker or external testing system rather than a domain-joined workstation, its DNS configuration was intentionally left unchanged.

For future Kerberos or domain-aware testing, Kali may temporarily query or use the domain controller's DNS service.

# 7. First SMB Authentication Attempt

The following command was issued from Kali:

```bash
smbclient -L //192.168.133.130 -U 'LIVINGENTERPRISE\auth.test'
```

The intention was to supply an incorrect password and produce a failed authentication event.

Instead, Kali returned:

```text
Sharename       Type
---------       ----

ADMIN$          Disk
C$              Disk
IPC$            IPC
NETLOGON        Disk
ServerTools     Disk
SYSVOL          Disk
```

The command later produced:

```text
Reconnecting with SMB1 for workgroup listing.

do_connect: Connection to 192.168.133.130 failed
(Error NT_STATUS_RESOURCE_NAME_NOT_FOUND)

Unable to connect with SMB1 -- no workgroup available
```

Initially this appeared ambiguous.

However, the fact that SMB shares had been enumerated strongly suggested that the authentication itself had succeeded.

The SMB1 message occurred afterward and represented a separate attempt to perform legacy workgroup enumeration.

The two outcomes therefore needed to be separated:

```text
SMB Authentication / Share Enumeration
              SUCCESS

Legacy SMB1 Workgroup Enumeration
              FAILED
```

The legacy SMB1 failure was not evidence that the original authentication had failed.

# 8. Investigating the Unexpected Successful Authentication

Because no new Event ID 4625 appeared, successful authentication events were queried.

```powershell
Get-WinEvent -FilterHashtable @{
    LogName='Security'
    Id=4624
    StartTime=(Get-Date).AddMinutes(-30)
} | Select-Object TimeCreated, Id, Message | Format-List
```

A critical event appeared at:

```text
9/13/2026 3:39:36 PM
```

## Event ID 4624

```text
An account was successfully logged on.
```

Relevant fields:

```text
Logon Type:             3

Account Name:           auth.test
Account Domain:         LEE

Workstation Name:       LEE-KALI-01
Source Network Address: 192.168.133.128
Source Port:            39044

Logon Process:          NtLmSsp
Authentication Package: NTLM
Package Name:           NTLM V2
Key Length:             128
```

This definitively proved that Windows had successfully authenticated `auth.test`.

## Interpretation

### Logon Type 3

Logon Type 3 represents a network logon.

This was expected because SMB authentication occurred remotely over the network rather than through an interactive console login.

### Source Workstation

```text
LEE-KALI-01
```

Windows identified the originating system.

### Source IP

```text
192.168.133.128
```

This directly correlated the event to the Kali testing system.

### Authentication Package

```text
NTLM
```

### NTLM Version

```text
NTLM V2
```

The SMB connection targeted the server by IP address:

```text
//192.168.133.130
```

rather than using its fully qualified domain name.

Using an IP address does not naturally provide the normal hostname-based CIFS Service Principal Name expected for Kerberos authentication. NTLM was therefore used for this authentication path.

This does not mean simply switching to a hostname will automatically create a Kerberos session; Kerberos also depends on appropriate DNS resolution, time synchronization, tickets, Samba configuration, and domain context.

# 17. Active Directory Account State After Controlled Failure

The account was checked again.

```text
SamAccountName         : auth.test
Enabled                : True
LockedOut              : False
BadPwdCount            : 1
LastBadPasswordAttempt : 9/13/2026 5:55:46 PM
```

One unexpected observation was that:

```text
BadPwdCount
```

changed from:

```text
2
```

to:

```text
1
```

rather than behaving like a cumulative counter.

This demonstrated an important point:

> `BadPwdCount` should not be interpreted as a simple historical count of every authentication failure.

Its value is influenced by Active Directory authentication and account-lockout behavior.

For forensic reconstruction, timestamped Windows Security events provide stronger evidence of exact authentication activity.

The following hierarchy was therefore used:

```text
4625 → Primary failed-logon evidence
4776 → Credential-validation evidence
4624 → Successful-logon evidence

LastBadPasswordAttempt → Supporting account-state evidence
BadPwdCount → Contextual account-state evidence
```

Before generating repeated failures, the domain password policy was examined.

```powershell
Get-ADDefaultDomainPasswordPolicy |
Select-Object `
    LockoutThreshold,
    LockoutDuration,
    LockoutObservationWindow,
    MinPasswordLength,
    PasswordHistoryCount,
    MaxPasswordAge |

```

Result:

```text

LockoutDuration          : 00:10:00
LockoutObservationWindow : 00:10:00
MinPasswordLength        : 7
PasswordHistoryCount     : 24
MaxPasswordAge           : 42.00:00:00
```

## Important Finding

```text
LockoutThreshold : 0
```

Account lockout was disabled.

This meant repeated authentication failures would not automatically lock the test account under the current policy.

Even though the lab account would not be locked, the automated test was intentionally kept small to minimize unnecessary activity and maintain a clean dataset.

This also demonstrated why authentication detections should consider environmental policy.

For example:

```text
5 failed attempts
```

may have very different meaning in an environment whose account-lockout threshold is:

```text
3
```

versus:

```text
10
```

or:

```text
0
```

# 20. Important Hydra Behavior

Hydra used up to four concurrent tasks.

This meant the initial expected sequence:

```text
Failure
Failure
Failure
Success
```

could not safely be assumed to represent the chronological order of events.

All four attempts could occur nearly simultaneously.

This reinforced an important forensic principle:

> Reconstruct activity from telemetry rather than assuming that tool input order equals event order.

Hydra began at approximately:

```text
18:16:05
```

and completed within several seconds.

Windows recorded all relevant authentication activity at:

```text
18:16:05
```

Because the attempts were concurrent and displayed only with second-level timestamps, the exact intra-second ordering cannot be proven from the collected output.

# 26. WORKGROUP Artifact

Hydra produced the warning:

```text
Workgroup was not specified, using "WORKGROUP"
```

Windows telemetry directly reflected that configuration.

The Hydra-generated failed 4625 events contained:

```text

WORKGROUP
```

This differed from the earlier manually generated SMB failure, which contained:

```text
Account Domain:
LIVINGENTERPRISE
```

The successful Hydra authentication resolved the authenticated identity as:

```text
Account Domain:
LEE
```

This demonstrated how attacker-tool configuration can influence defender-side telemetry.

It also reinforced that analysts should not assume a domain-related field will always contain the organization's normal domain value.

Unexpected domain values such as:

```text
WORKGROUP
```

may provide additional investigative context.

They are not independently proof of malicious activity.

# 30. IOC vs Behavioral Indicator

An important lesson from the exercise was that individual values are not automatically indicators of compromise.

For example:

```text
192.168.133.128
```

is only an IP address.

Likewise:

```text
Event ID 4625
```

only indicates a failed authentication.

Users mistype passwords regularly.

Similarly:

```text
NTLM
```

can exist in legitimate Windows environments.

The more meaningful signal comes from correlation.

Example:

```text
Same Source IP
        +
Same Account
        +
Multiple Authentication Failures
        +
Short Time Window
        +
Successful Authentication
        ↓
Potential Credential Attack
```

This shifts the analysis from:

```text
IOC matching
```

toward:

```text
Behavioral detection
```

A future SIEM detection could search for:


This pattern could indicate:

- password guessing
- brute-force activity
- compromised credentials

# 34. Evidence vs Inference

A major lesson from this exercise was distinguishing what logs prove from what an analyst believes likely occurred.

## Confirmed Evidence

Windows confirmed:

```text
Three failed logons occurred.
One successful logon occurred.
All involved auth.test.
All originated from LEE-KALI-01.
The source IP was 192.168.133.128.
The authentication occurred using NTLM.
The activity occurred in the same one-second window.
The failures resulted from incorrect passwords.
```

## Inference

It would be reasonable to infer:

```text
The attempts were generated by the same automated credential-testing operation.
```

This inference is strongly supported because the Hydra execution was known and controlled.

However, exact attempt ordering cannot be proven using the displayed second-level timestamps alone.

Therefore the documentation avoids claiming:

```text
three failures occurred first
and then the success occurred last
```

even though the password file was constructed in that order.

Hydra concurrency makes that conclusion unsafe without higher-resolution evidence.

# 35. Troubleshooting and Lessons Learned

## Lesson 1 — Expected Results Are Not Evidence

The first SMB attempt was expected to fail.

It did not.

Rather than assuming the command behaved as intended, Windows telemetry was examined.

That led to the discovery of:

```text
4624
4776
NTLMv2
successful SMB authentication
```

The lesson:

> Analysts must follow evidence rather than expectations.

---

## Lesson 2 — Successful Authentication Does Not Equal Authorization

The successful SMB authentication returned shares including:

```text
ADMIN$
C$
```

This did not mean `auth.test` had permission to access those administrative shares.

Authentication and authorization are separate concepts.

```text
Authentication:
Who are you?

Authorization:
What are you allowed to access?
```

A system may enumerate the existence of resources without granting access to their contents.

---

## Lesson 3 — SMB1 Errors Were Separate from Authentication

The message:

```text
Unable to connect with SMB1
```

occurred after successful SMB authentication and share enumeration.

It represented legacy workgroup-enumeration behavior rather than failure of the original SMB authentication.

This demonstrated the importance of separating multi-stage command output.

---

## Lesson 4 — DNS Problems May Not Be Domain Controller Problems

The failed lookup of:

```text
LEE-WIN-SRV-01.livingenterprise.lab
```

was initially suspicious.

Investigation showed Kali was querying:

```text
192.168.133.2
```

rather than:

```text
192.168.133.130
```

The domain DNS service itself was healthy.

This reinforced:

```text
Connectivity ≠ Service Availability ≠ Name Resolution
```

---

## Lesson 5 — Event Logs Are Noisy

Initial 4624 searches returned significant background domain-controller activity including:

- machine-account authentications
- Kerberos activity
- service logons
- local authentication events
- administrative activity

The relevant event became clear only after filtering by:

```text
account
source
time
event ID
```

This closely resembles real SOC investigations.

---

## Lesson 6 — Narrow Time Windows Improve Analysis

Broad event searches generated excessive noise.

Exact time windows around known activity dramatically improved investigation quality.

For example:

```powershell
StartTime=[datetime]'2026-09-13 18:15:30'
EndTime=[datetime]'2026-09-13 18:16:30'
```

This approach will become increasingly important when analyzing larger SIEM datasets.

---

## Lesson 7 — Multiple Event IDs Tell Different Parts of the Story

### 4776

Answered:

```text
Were the credentials successfully validated?
```

### 4624

Answered:

```text
Was a Windows logon session successfully created?
```

### 4625

Answered:

```text
Did the requested logon fail, and why?
```

Together they provided a much stronger reconstruction than any single event.

---

## Lesson 8 — Account State Is Supporting Evidence

`LastBadPasswordAttempt` correlated accurately with observed failure timestamps.

However:

```text
BadPwdCount
```

did not behave like a simple cumulative historical counter.

Therefore:

> Use timestamped Security logs for exact forensic reconstruction and account attributes for supporting context.

---

## Lesson 9 — Tool Configuration Appears in Defender Telemetry

Hydra reported:

```text
Workgroup was not specified, using WORKGROUP
```

Windows subsequently recorded:

```text
Account Domain: WORKGROUP
```

This directly demonstrated how attacker tooling can influence defender-visible artifacts.

---

## Lesson 10 — Concurrent Activity Complicates Timelines

Hydra used:

```text
max 4 tasks
```

Windows recorded all four credential validations at:

```text
18:16:05
```

Second-level timestamps were insufficient to establish exact intra-second ordering.

Therefore:

> Do not claim ordering that the collected evidence cannot prove.

# 36. Security Operations Takeaways

This lab reinforced several core SOC analyst skills:

### Baseline before investigating.

Understanding normal account and system state makes abnormal activity easier to identify.

### Generate known activity when possible.

Controlled tests create known ground truth that can be compared against telemetry.

### Correlate across multiple data sources.

A single event rarely tells the entire story.

### Filter aggressively.

Useful correlation fields included:

```text
Event ID
Username
Source IP
Source workstation
Timestamp
Authentication protocol
Logon type
Status code
Substatus code
```

### Interpret behavior, not just indicators.

An isolated failed login is common.

Repeated failures plus success from the same source are more meaningful.

### Separate evidence from inference.

Good investigations clearly state what is confirmed and what is hypothesized.

### Investigate unexpected results.

Unexpected behavior may provide the most valuable learning opportunity in a lab.
