### 4.1 SCA 36503 — Minimum password length

**Evidence:** E-01, E-02. **Observed:** 7 characters. **Required:** at least 14 characters.

**Exact supplied check, condition `all`:**

```text
c:powershell secedit /export /cfg $env:TEMP\secpol.cfg; Get-Content $env:TEMP\secpol.cfg | Select-String "MinimumPasswordLength"; Remove-Item $env:TEMP\secpol.cfg -> n:MinimumPasswordLength = (\d+) compare >= 14
```

**Group Policy location:** `Computer Configuration\Policies\Windows Settings\Security Settings\Account Policies\Password Policy\Minimum password length`.

**Interpretation:** The reported default minimum does not meet this check. It permits shorter passwords than the candidate baseline; it does not prove any existing account has a seven-character password. Increasing a minimum is not evidence that existing passwords have already been replaced.

**Risk:** A lower permitted minimum can make weak credential selection easier and reduce resistance to guessing or cracking. Length alone does not establish password quality or account security.

**Candidate:** 14 characters. Validate dependencies and use dedicated test-account password changes to demonstrate enforcement during the later hardening phase.

### 4.2 SCA 36505 — Account lockout duration

**Evidence:** E-01, E-02. **Observed:** 10 minutes. **Required:** at least 15 minutes.

**Exact supplied check, condition `all`:**

```text
c:powershell secedit /export /cfg $env:TEMP\secpol.cfg; Get-Content $env:TEMP\secpol.cfg | Select-String "LockoutDuration"; Remove-Item $env:TEMP\secpol.cfg -> n:LockoutDuration = (\d+) compare >= 15
```

**Group Policy location:** `Computer Configuration\Policies\Windows Settings\Security Settings\Account Policies\Account Lockout Policy\Account lockout duration`.

**Interpretation:** Ten minutes fails the numeric requirement. With the reported threshold of zero, this timer does not by itself enable automatic lockout. Do not describe current accounts as automatically unlocking after ten minutes as a consequence of failed-attempt lockout under this default policy.

**Risk:** Once automatic lockout is enabled, duration affects both attack throttling and user availability. A longer duration can prolong accidental or deliberately induced denial of service.

**Candidate:** 15 minutes. A value of zero for duration means administrator unlock is required when lockout applies; it is different from threshold zero and does not satisfy the supplied `>= 15` check.

### 4.3 SCA 36506 — Account lockout threshold

**Evidence:** E-01, E-03. **Observed:** 0. **Required:** 1–5 invalid attempts inclusive.

**Exact supplied checks, condition `all`:**

```text
c:powershell secedit /export /cfg $env:TEMP\secpol.cfg; Get-Content $env:TEMP\secpol.cfg | Select-String "LockoutBadCount"; Remove-Item $env:TEMP\secpol.cfg -> n:LockoutBadCount = (\d+) compare <= 5
c:powershell secedit /export /cfg $env:TEMP\secpol.cfg; Get-Content $env:TEMP\secpol.cfg | Select-String "LockoutBadCount"; Remove-Item $env:TEMP\secpol.cfg -> n:LockoutBadCount = (\d+) compare > 0
```

**Group Policy location:** `Computer Configuration\Policies\Windows Settings\Security Settings\Account Policies\Account Lockout Policy\Account lockout threshold`.

**Interpretation:** Both comparisons must pass. Zero meets the upper bound but fails the nonzero requirement. Zero disables automatic lockout under this policy; it is not a lockout on the first invalid attempt. No actual compromise or successful guessing is established by this configuration finding.

**Correction:** The earlier conversation pasted the 36505 duration description and check beneath 36506. The subsequent threshold-specific remediation and `LockoutBadCount` checks replace that mistaken association.

**Risk:** Repeated password guesses are not stopped by this lockout mechanism. Enabling a low threshold also creates opportunities for accidental lockout and deliberate account denial of service.

**Candidate:** 5 invalid attempts, chosen from the allowed 1–5 range. Five is a proposed operating choice, not the only passing value. Do not substitute a different vendor baseline and still label it compliant with this supplied check.

### 4.4 SCA 36507 — Reset account lockout counter after

**Evidence:** E-01, E-04. **Observed:** 10 minutes. **Required:** at least 15 minutes.

**Exact supplied check, condition `all`:**

```text
c:powershell secedit /export /cfg $env:TEMP\secpol.cfg; Get-Content $env:TEMP\secpol.cfg | Select-String "ResetLockoutCount"; Remove-Item $env:TEMP\secpol.cfg -> n:ResetLockoutCount = (\d+) compare >= 15
```

**Group Policy location:** `Computer Configuration\Policies\Windows Settings\Security Settings\Account Policies\Account Lockout Policy\Reset account lockout counter after`.

**Interpretation:** `LockoutObservationWindow` is the AD property corresponding to this counter-reset interval. Ten minutes fails the supplied check. Counter reset is distinct from unlocking a locked account. When a nonzero threshold is used, the reset interval must be less than or equal to lockout duration.

**Risk:** The interval changes how failures accumulate and interacts with user error and attacker pacing. Its present practical lockout significance is limited by threshold zero; it remains a separate configuration failure.

**Candidate:** 15 minutes, paired with a duration of 15 minutes.

### 5.1 Policy scope and authority

The supplied Wazuh remediation text directs configuration through the **Default Domain Policy** for default domain-account behavior and notes PSO exceptions. Treat that as the documented implementation path for this project. Do not assume an OU-linked computer policy changes the default policy for AD domain users.

Before any change, confirm domain-root policy scope, precedence, the source of effective domain settings, and applicable fine-grained password policies. The AD default-domain query establishes default domain values; a `secedit` export records security-policy values on the assessed computer. They are related evidence sources, not interchangeable proof of every user's effective policy. A PSO can give selected users a different policy ([Microsoft default-domain query documentation](https://learn.microsoft.com/en-us/powershell/module/activedirectory/get-addefaultdomainpasswordpolicy?view=windowsserver2025-ps), [resultant PSO documentation](https://learn.microsoft.com/en-us/powershell/module/activedirectory/get-aduserresultantpasswordpolicy?view=windowsserver2025-ps)).

## 6. Risk disposition and deferred remediation

**Disposition:** Retain the documented baseline temporarily for controlled lab simulations; keep all four findings open. This records the requested project direction, not formal enterprise risk acceptance.

Preserving the baseline can support repeatable before/after comparisons of authentication failures, password-guessing detections, alert timing, and subsequent lockout behavior. Immediate hardening would change the conditions being measured. That experimental value does not remove the exposure associated with short permitted passwords and disabled automatic lockout.

Recommended conditions for the deferral are lab isolation, dedicated nonprivileged test identities, synthetic credentials, bounded attempts, verified telemetry, and a documented recovery route. These are proposed controls; their presence has not been verified. Restrict simulations to authorized lab targets. Do not use production accounts or treat an unverified recovery snapshot as a complete AD recovery plan.

**Revisit triggers:** completion of the planned baseline simulations; any expansion of exposure or trust; use of real credentials; unexpected account impact; evidence of uncontrolled activity; or entry into Phase 7 v17. Any trigger should prompt review of whether continued deferral is justified.

**Outstanding governance:** owner, approver, review date, simulation completion criteria, and exception expiration are unassigned. Set these before operational simulations. No formal risk score is assigned without exposure, asset criticality, and compensating-control evidence.

Microsoft documents both the guessing risk of threshold zero and the denial-of-service tradeoff of lockout, as well as the timer relationship. Its separate baseline guidance must not be substituted for this register's CIS check criteria ([Microsoft account lockout threshold](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/security-policy-settings/account-lockout-threshold)).

## 7. Validation and evidence collection

Run these commands on an authorized domain management host or DC with the required modules and access. Record timestamp, host, target domain/DC, account context, command, output, and errors. These are collection instructions, not evidence of execution. They do not change password or lockout policy.

### 7.1 Query the default domain policy explicitly

```powershell
Import-Module ActiveDirectory
$domain = Get-ADDomain
$dc = $domain.PDCEmulator
Get-Date -Format o
$env:COMPUTERNAME
$domain | Select-Object DNSRoot, DistinguishedName, PDCEmulator
$policy = Get-ADDefaultDomainPasswordPolicy -Identity $domain.DNSRoot -Server $dc
$policy | Format-List MinPasswordLength, LockoutThreshold, LockoutDuration,
    LockoutObservationWindow, PasswordHistoryCount, MaxPasswordAge,
    MinPasswordAge, ComplexityEnabled, ReversibleEncryptionEnabled
```

For multi-DC environments, repeat against the relevant DCs and investigate discrepancies rather than silently selecting the preferred result.

### 7.2 Evaluate the four candidate predicates against AD values

```powershell
# Requires $policy from the preceding query.
[pscustomobject]@{
    SCA36503_ADPredicate = ($policy.MinPasswordLength -ge 14)
    SCA36505_ADPredicate = ($policy.LockoutDuration.TotalMinutes -ge 15)
    SCA36506_ADPredicate = (($policy.LockoutThreshold -gt 0) -and
                           ($policy.LockoutThreshold -le 5))
    SCA36507_ADPredicate = ($policy.LockoutObservationWindow.TotalMinutes -ge 15)
    TimerRelationship = ($policy.LockoutObservationWindow -le $policy.LockoutDuration)
}
```

These Boolean results compare AD values with the supplied criteria. They do not reproduce the Wazuh execution context or replace a fresh SCA result. An export failure or missing numeric match must be investigated as a collection/check problem, not silently interpreted as a passing value.

### 7.3 Reproduce the security-policy export on the assessed host

Use an elevated shell where required. This alternative uses a unique temporary filename and cleans up only that file. The exact historical SCA commands remain preserved above.
